# Follow-up testing — 13 November 2026

**Experimental. The new CUDA contract tests use small tensors, not full model
weights. Full fixed-text Q4 results were subsequently measured and are recorded
in the [quality report](Q4_RESULTS_2026-11-13.md); Q4 did not pass acceptance.**

## Two CUDA ordering defects found and repaired

**Per-slot consumer completion.** With two slots acquired by different CUDA
streams, releasing the first slot used the pipeline's most recently acquired
stream. A real-event observer reproduced this wrong stream assignment. Output
values happened to remain correct in that short run, so that observation alone
did not prove data corruption. Each slot now retains its own consumer stream,
and its release event is recorded on that stream.

**First DMA versus arena initialization.** The arena was zero-initialized on
the construction stream, while its first H2D write ran on a new transfer stream
without an ordering dependency. A reuse stress test returned zero instead of
the first expected value in all three tested slot configurations. The transfer
stream now waits for construction-stream initialization. This inserts a GPU
dependency; it does not add a CPU wait before every operation.

After both changes, a dedicated delayed-construction test also passed with
arena creation and consumption on different streams.

## Verification

The combined targeted regression run returned **37 passed in 10.64 seconds**:

- Correct event ownership for concurrent consumers.
- First DMA ordered after delayed arena initialization.
- 1,024 reuses each for one, two and three slots: **3,072 total**, with exact
  output checks, immediate host-buffer overwrites and alternating consumers.
- Lifetime counters continue beyond the 4,096-record bounded event history.
- Closing during an observed in-flight tail prefetch drains its DMA safely;
  repeated close succeeds.
- Existing ring, pinned-race, cache, native admission, OLMoE synthetic forward,
  quality-metric and resource-guard regressions.

The in-flight close test proves synchronized teardown. It is **not** a general
asynchronous prefetch-cancellation API or dynamic VRAM-placement implementation.
This short stress run is also not a multi-hour soak test.

## Q4 quality work and resource boundary

A real Qwen BF16 smoke run completed on 12 prefixes × 2 steps: 64 layer loads
and 64 computes, finite logits, peak Torch CUDA allocation about 3.125 GiB.
It was performed before the two ordering fixes and is not their full-model
regression proof. Its 24 positions included only 15 confident positions, so it
does not satisfy the quality sample-size requirement.

The probe took about 28 seconds per forward step on this machine. A new
[fixed-text protocol](QUALITY_EVALUATION.md) collects all position logits from
the existing head, giving 960 positions in five batched passes. It preserves
the strict acceptance thresholds and records reusable, hashed BF16 reference
artifacts. No Q4 quality thresholds have been relaxed.

The first fixed-text attempt was stopped by the unchanged 2.8 GiB available
RAM guard before model initialization. A subsequent attempt recorded
`SAFE_SKIP`, with 2,590,277,632 bytes (about 2.412 GiB) available after Python
imports. Neither attempt produced fixed-text model results.

The smoke runner also retained a local reference to its last observed layer,
leaving about 426 MiB allocated at its cleanup measurement. That reference
has been removed from the new runner; a full-model cleanup remeasurement is
still required. Do not interpret this as a demonstrated core-model memory leak.

This was the resource boundary at the end of this pass. After memory was freed,
the full fixed-text reference, repeatability and Q4 runs completed. The retained
layer fix was remeasured at 8.125 MiB after close. See the
[subsequent quality results](Q4_RESULTS_2026-11-13.md); BF16 remains the default.
