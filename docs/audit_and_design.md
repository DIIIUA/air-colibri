# Аудит исходного кода AirLLM и Colibrì и архитектурный дизайн AirColibri

## 1. Детальный аудит AirLLM (`upstream_airllm`)

### 1.1. Исследованные файлы и функции
- `air_llm/airllm/airllm_base.py`:
  - `AirLLMBase.__init__` (строки 45–120): инициализация мета-модели через HuggingFace `accelerate` (установка всех параметров на устройство `'meta'`).
  - `_load_layer_to_cpu(layer_idx)` (строки 135–170): поиск шардов safetensors на диске и десериализация весов слоя в обычную оперативную память (RAM).
  - `_load_layer_to_device(layer_idx)` (строки 175–205): динамическое перемещение параметров слоя на GPU через `module.to(self.device)`.
  - `_clean_up_layer(layer)` (строки 210–240): сброс параметров в `torch.empty(0, device='meta')`, принудительный вызов `gc.collect()` и `torch.cuda.empty_cache()`.
  - `_pre_hook` / `_post_hook` (строки 245–285): PyTorch forward-хуки, управляющие жизненным циклом слоя на каждом токене.

### 1.2. Критические узкие места и архитектурные дефекты AirLLM
1. **Накладные расходы аллокатора и `torch.cuda.empty_cache()`:**
   - Вызов `torch.cuda.empty_cache()` после каждого слоя сбрасывает закэшированные блоки памяти PyTorch обратно в драйвер NVIDIA.
   - Это приводит к полной синхронизации GPU пайплайна (driver fence) и повторным системным вызовам `cudaMalloc` на следующем слое. Накладные расходы составляют от 10 до 40 мс на каждый слой каждого токена.
2. **Отсутствие перекрытия вычислений и передачи (No Overlap):**
   - Выполнение строго последовательное: чтение слоя $i$ $\rightarrow$ передача по PCIe $\rightarrow$ вычисление GEMM $\rightarrow$ удаление $\rightarrow$ переход к слою $i+1$. Вычислительные блоки GPU простаивают во время передачи весов по шине PCIe.
3. **Отсутствие гранулярности на уровне MoE-экспертов:**
   - Для моделей со смесью экспертов (MoE) AirLLM оперирует слоем целиком. Если в модели 64 эксперта по 500 МБ (слой 32 ГБ), AirLLM загружает все 32 ГБ, хотя активны лишь 2 эксперта (1 ГБ). Это делает запуск 200B+ MoE моделей на потребительском железе катастрофически медленным.

## 2. Детальный аудит Colibrì (`upstream_colibri`)

### 2.1. Исследованные файлы и функции
- `c/cu_tier.c` и `c/cu_tier_ops.h`:
  - `cut_init(...)`: инициализация постоянного пула слотов в VRAM GPU без последующих вызовов `cudaMalloc` во время инференса.
  - `cut_alloc_bytes`: строгий расчёт выравнивания строк (256 байт) и форматов квантования (INT4, FP8, IQ3).
- `c/tier.h`:
  - `tier_should_promote(hot, cold)`: проверка порога с запасом 25% (`hot > cold + (cold >> 2) + 4`) для предотвращения «пинг-понга» (дребезга) слотов при близких частотах роутинга.
  - `tier_lfru_score(heat, last, clock)`: гибридная оценка частоты (старшие биты) и свежести обращения (младшие 8 бит, 0..255).
  - `tier_decay_value(heat)`: экспоненциальное остывание (`heat >> 1`).
- `c/compat_prefetch_win.h`:
  - Асинхронное чтение через Win32 API (`FILE_FLAG_OVERLAPPED`, `PrefetchVirtualMemory`, `CreateFileA`).
- `c/pin_pool.h`:
  - Пул закреплённой (pinned/page-locked) памяти хоста, обеспечивающий прямой DMA доступ GPU через PCIe без участия ядра CPU.
- `c/qwen36.c`:
  - Основной цикл генерации токенов, управление линейным вниманием DeltaNet и диспетчеризация вычислений на CUDA-потоках.

### 2.2. Преимущества и ограничения Colibrì
- **Преимущества:** Экстремальная скорость передачи весов (до физического лимита PCIe 4.0 x16 / x8), полное отсутствие аллокатора во время генерации, эффективное удержание горячих экспертов в VRAM по алгоритму LFRU.
- **Ограничения:** Colibrì предполагает, что плотная часть (Dense backbone, Attention) целиком помещается в доступную память хоста/GPU, а потоково подкачиваются только разреженные эксперты MoE. Если модель имеет плотный размер 70B (Llama-3-70B), Colibrì не сможет запустить её на 8 ГБ VRAM без сброса слоев плотной сети.

## 3. Архитектура гибридного движка AirColibri

AirColibri объединяет послойный свопинг AirLLM и нативную производительность слотов Colibrì:

```
┌────────────────────────────────────────────────────────────────────────┐
│                        AirColibri Hybrid Engine                        │
├────────────────────────────────────────────────────────────────────────┤
│  1. Unified Persistent Slot Pool (GPU VRAM + Host Pinned RAM)          │
│     - Нулевая фрагментация: фиксированные слоты выделяются один раз    │
│     - Запрет на cudaMalloc/cudaFree/empty_cache в цикле инференса      │
├────────────────────────────────────────────────────────────────────────┤
│  2. Dense Backbone: Double Buffering Stream Overlap                    │
│     - Слот 0: вычисление Attention/GEMM на compute_stream              │
│     - Слот 1: асинхронный DMA-трансфер слоя i+1 на transfer_stream     │
│     - Синхронизация через cudaEvent بدون блокировки CPU                │
├────────────────────────────────────────────────────────────────────────┤
│  3. MoE Sparse Experts: Persistent LFRU Slot Cache                     │
│     - M постоянных слотов для экспертов в VRAM                         │
│     - Горячие эксперты остаются резидентными (0 байт трансфера)       │
│     - Холодные эксперты вытесняют кандидатов по правилу 25% запаса     │
└────────────────────────────────────────────────────────────────────────┘
```
