Как читать

Начало: получение/подготовка checkpoint, выбор executor, размещение постоянных объектов. Середина: read → размещение → compute → release в пределах слоя и прохода. На всём протяжении: скрытые состояния, память, статистика, worker-ы, синхронизация, ошибки. Конец: завершение token/pass/request отличается от shutdown объекта/process.

На схемах «загружено» означает готовый payload, а «записано событие» ещё не означает завершённый GPU consumer. Файл checkpoint, OS page cache, owned CPU payload, CUDA pinned memory, device weights и KV/recurrent state — разные объекты. У каждого должна быть своя граница lifetime.

Что мы раньше рисковали пропустить

  1. Одинаковая C-функция не воспроизводит оригинальную политику целиком. В AirColibri NativeTierPolicy старит heat каждые 100 access events. В GLM tier_pick_lfru вызывается с per-layer arrays в контексте REPIN/emitted tokens; у common GPU tier другой token clock, placement classes, promotion budget и период decay. Это наблюдаемое различие, а не доказанная причина нулевых hits последнего extended теста. [I01, C10, C15]
  2. Наш общий GPU-кэш и исходный OLMoE CUDA chain имеют разную топологию. Исходный chain требует residency всех экспертов; при недостатке VRAM выбирается CPU path. Наш путь переносит выбранные BF16 experts через небольшой Ring и вычисляет HF/PyTorch math. [I02–I04, C11]
  3. В оригинале есть связь веса ↔ растущий state. OLMoE kv_room_fit() сокращает RAM slots при росте KV; host pool tier тоже может забрать часть room. Наш startup plan и отдельные guards пока не являются общим динамическим ledger всех allocations. [C07, C10, I05]
  4. Prefetch — несколько разных механизмов. CPU next-module read, PILOT prediction, tier uploader и наш CUDA tail-to-head не имеют одного взаимозаменяемого API. Им нужны разные readiness, cancellation/stale и ownership contracts. [A04, C09–C13, I04]
  5. Роутинг и размещение нельзя незаметно смешивать. PILOT не подменяет истинный top-K; optional CACHE_ROUTE может его изменить. Для сохранения математической эквивалентности эти варианты должны иметь отдельные quality/parity criteria. [C08, C16]
  6. Prefill и decode дают разные события reuse. Native OLMoE группирует rows по экспертам; его hit counter включает часть внутрибатчевого reuse. Наш счётчик запросов loader-а имеет другую семантику. Сравнивать проценты без определения знаменателя нельзя. [C08, I02]
  7. Переезд вычисления требует переезда актуального state. KV, DeltaNet, convolution state, positions, prefix ledger и иногда RNG/sampling context относятся к executor seam. Перенос только tensor weights не создаёт рабочее progressive CPU→GPU подключение. [C11, C14, C17]
  8. У оригиналов разные окончания процесса. AirLLM не даёт общего close/drain API в этом пути; Colibrì имеет несколько разных shutdown contracts. Объединение должно явно определить завершение consumers и pending reads до освобождения buffers. [A04, C05, C09–C13]

Текущее AirColibri — отдельная третья схема

Здесь «существующий/original Ring» означает Ring существовавшего проекта AirColibri, а не класс из авторского AirLLM. Реально перенесённые части: subset reader и C scoring functions. Reader namespace/backend binding, byte budgets, shared arenas, lifecycle ACKs, event cadence и HF adapters принадлежат нашей интеграции. Full native Colibrì model executor не подключён.

Поэтому положительные integration tests доказывают корректность данного пути и его границ на выбранных workloads, но не полноту переноса каждого исходного механизма.

Следующий порядок объединения, выведенный из карт

Подробное распределение ответственности, стадий и временных окон — в плане объединения точек пересечения.

  1. Зафиксировать один маршрут: точный checkpoint/family, format, HF/reference version, CPU/GPU executor и state layout. Для каждого эксперимента явно записать, какой native path сопоставляется с нашим, вместо общего названия «Colibrì».
  2. Нормализовать события и единицы: token / row / forward / layer / expert request, область candidate comparison, clocks/decay, logical read bytes и physical I/O отдельно. Сначала trace/replay на сохранённых route IDs; не менять math ради cache hits.
  3. Описать переносимый контракт объекта: identity/version/format/bytes, место, владелец, readiness, consumer completion, cancellation/stale, reservation и failure outcome. Подтверждение placement должно отражать фактический backend result.
  4. Связать бюджеты со state: globals + Dense/expert weights + pinned/staging + scratch + KV/recurrent/native buffers. Перед admit/prefetch/shrink учитывать весь актуальный объём, проверять backpressure и порядок освобождения, а не суммировать только веса.
  5. Переносить по одному механизму: сначала matched policy trace, затем CPU-read prefetch, затем device residency; каждый раз off/shadow/apply, exact routes/state/logits и latency/memory. Native executor/state migration — отдельный следующий этап с независимой проверкой чисел.
  6. Проверить lifetime на конце и отказе: last→first, следующий request, cancel, read failure, device fallback, close/reopen; ни один pending consumer не должен видеть перезаписанный payload.

Это план после source-аудита, не перечень уже реализованных возможностей. Новые integration изменения по этой карте в данном проходе не делались.

1. Кто управляет процессом

В основной PyTorch-ветке AirLLM создаёт настоящую модель Transformers с параметрами на meta. Transformers выполняет модельный forward и цикл generate; AirLLM ставит hooks на границы модулей, чтобы материализовать нужные веса перед вычислением и вернуть их на meta после него. Токенизатор, маршрутизатор MoE, attention, KV/recurrent state и критерии генерации относятся к конкретной HF-модели. AirLLM не заменяет их единым собственным вычислительным графом. [A01–A04]

generate() и forward() просто делегируют вызов HF-модели. Обычный forward() сам по себе не означает генерацию до EOS: повторные вызовы и передача cache могут принадлежать приложению. Автоматический долговременный сервер диалогов в этом пути не создаётся. [A04]

3. Середина: один модуль и перекрытие чтения

Последовательность в _pre_hook: получить CPU state → переместить текущие веса → отправить чтение следующего модуля на CPU. Это не предварительная DMA следующего модуля в отдельный GPU-ring slot. В просмотренном основном пути нет своего copy-stream/event/lease протокола. Синхронизация устройства и lifetime tensor storage остаются за PyTorch/Accelerate. [A04]

load_layer_to_cpu() может скопировать CPU tensors в pinned memory, если включён prefetch, выбрана CUDA и размер слоя не превышает 2 GiB. При ошибке pinning остаются обычные CPU tensors. Это условное свойство whole-layer пути, не гарантия для каждого load_layer_subset(). [A03, A07]

Следующий индекс — следующий элемент списка streamed-модулей. Автоматического замыкания последнего слоя на первый слой следующего token-pass здесь нет. Наш prefetch_tail_to_head() нельзя приписывать исходному AirLLM. [A04]

5. Развилки, которые нельзя потерять

5.1. Обычный слой и выборочные эксперты

expert_prefix в проверенной версии задаётся Kimi K3 wrapper. Наличие универсальной функции load_layer_subset() не означает, что AirLLM автоматически выполняет выбранных экспертов OLMoE тем же способом. Qwen4-Exp хранит packed 3D experts на одном модуле; его wrapper прямо оставляет whole-layer streaming. [A04, A09–A11]

5.3. macOS / MLX — отдельный executor

AutoModel выбирает AirLLMLlamaMlx на macOS и отклоняет явно указанную архитектуру вне Llama/Mistral. Пустое поле architecture проходит эту проверку, но не доказывает совместимость. Это собственные MLX Attention, TransformerBlock, RMSNorm, sampling и Python generator, а не HF forward с hooks. Persister сохраняет .mlx.npz; меняет имена параметров под MLX. [A01, A08, A12]

test_nonlayered=True сохраняет modules вместо повторного удаления/создания. В обычной layered ветке веса читаются снова на decode. Явные mx.eval — границы ленивого вычисления, существенно отличающиеся от основного PyTorch hook-пути. В просмотренном wrapper выход внешнего generate ограничен числом новых токенов; не следует переносить на него весь набор HF stopping rules.

5.4. LoRA training — дополнительная, не inference-ветка

AirLLMLoRA / AirLLMLoRAQwen4Exp отключают обычные streaming hooks и используют custom autograd: forward слоя → CPU-сохранение hidden → eviction base weights → loss → backward с повторной загрузкой frozen base weights и recompute → gradients LoRA → optimizer step → сохранение adapter. LoRA-параметры и optimizer state живут отдельно от выгружаемых base weights. Это дополнительный проход по весам в обратном порядке, отсутствующий в обычной генерации. [A13]

6. Конец прохода, следующий запрос, остановка и ошибки

  1. Конец слоя: post-hook снимает материализованные параметры; hidden/state нужны последующим операциям.
  2. Конец forward: HF возвращает output; будущий decode снова пройдёт streamed-модули с сохранённым state.
  3. Конец generate: управление возвращается приложению; model, hooks, resident modules и executor ещё существуют.
  4. Следующий запрос: файлы split и сам объект переиспользуются. Сохранение/повторная передача cache определяется caller/HF, а не общим AirLLM session manager.
  5. Остановка: отдельного complete/drain/release протокола для всех ресурсов в проверенном пакете не найдено. Нельзя рисовать симметричный close() только потому, что такой API есть в AirColibri.
  6. Ошибка чтения/материализации/forward: исключение выходит по Python-пути. В исследованном hook-коде нет единого recovery state machine с отменой pending prefetch и подтверждением освобождения CUDA consumers.

7. Границы доказательства и что измерять при переносе

Разобраны внешние входы, preparation/persistence, главный hook-путь, resident/CPU-mmap данные, expert specialization, MLX и LoRA lifecycle. Не выполнялась проверка каждой поддержанной архитектуры, каждого quantizer, каждой версии HF и всех exceptional paths. Математика внешней HF-модели — отдельный контракт; её версию и state layout нужно фиксировать для конкретного checkpoint.

Минимальный trace для проверки схемы на модели: request/pass/layer/expert IDs → начало/конец логического чтения → CPU/pinned bytes → materialize → compute dependency → release → KV/state bytes. Нужно отдельно мерить physical I/O и peak RAM/VRAM: количество loader calls их не заменяет.

Обозначения источников A01–A13 разрешаются в реестре с revision, SHA-256 и строками.

1. Верхний уровень: это семейство движков

Colibrì состоит из Python control plane, семейства native executors и общих подсистем хранения, телеметрии, RAM/GPU tiers, state и serving. c/colibri.c — GLM-движок, а не универсальный forward для всех моделей. c/tier.h — небольшая библиотека оценки, а не весь control plane. [C01–C04]

3. Начало text inference: что и куда загружается

Конкретные формы различаются. OLMoE CPU читает converted merged_weight + qs либо GGUF blocks; слот содержит native gate/up/down payload и scales, а не Python BF16 state_dict. Loader проверяет форму/размер перед записью. Шардовый st.h поддерживает адресные чтения, optional mappings и platform-dependent I/O; файл и OS page cache остаются отдельными уровнями. [C06, C07]

Для Dense-моделей ветка экспертов может отсутствовать полностью. В qwen36 Dense MLP остаются resident; экономия на cold experts к ним автоматически неприменима. Одного названия «streaming engine» недостаточно, чтобы сделать вывод о послойной выгрузке всех Dense weights. [C14]

4. OLMoE CPU: точный путь внутри одного forward

Это подробно разобранный native CPU путь для семейства, которое используется в текущем AirColibri MoE experiment. Его нельзя автоматически переносить на GLM/Qwen. [C06–C09]

При chain backend финальный head может быть уже выполнен на device к моменту обновления host token counters/prefix. Группировка prefill обрабатывает эксперта для нескольких выбранных строк за одно получение слота. Поэтому число cache hits в оригинале может включать повторное применение внутри batch; сравнивать его с cache-hit counter нашего per-expert loader без нормализации нельзя. [C08]

RAM-слот: владение и конкурентное чтение

expert_get выполняет lookup в cache конкретного layer. При miss выбирает свободный slot или victim; не перезаписывает busy/in-flight payload. Demand read при необходимости ждёт condition variable. Резервирование и публикация происходят под mutex, само чтение — вне lock. Demand-get на freshly loaded slot публикует его сразу занятым для потребителя. [C07]

pinned в Slot означает запрет обычной эвикции hot expert, а не CUDA pinned host memory. Это разные свойства с разными владельцами. Под давлением demand path может снять pin, но не перескакивает защиту busy/in-flight. [C07]

PILOT: отдельный speculative read path

После attention residual прогнозируется router будущего слоя; PILOT>=2/3 расширяет lookahead после текущего MoE residual. Используются destination norm/router, optional smoothing и confidence, затем очередь запросов worker-у. Данные читаются в RAM expert cache. Это не замена результата настоящего router и не CUDA tail-to-head transfer. [C08, C09]

Worker пропускает устаревшие, уже resident/in-flight и недопустимые заявки. LFRU guard может отказать speculative replacement тёплого resident expert. Новому forward не нужно откатывать ring queue indices: очищаются queued marks, worker дренирует stale entries. OLMoE PILOT worker создаётся detached и имеет бесконечный цикл; CLI model сделана static, чтобы worker не получил висячий pointer перед exit. Универсального join этого worker в CLI-пути здесь нет. [C07, C09]

KV растёт — RAM cache сокращается

kv_room_fit() вызывается перед записью следующих позиций. Из общего room вычитается KV, пересчитывается число slots/layer, вытесняются допустимые LRU entries, при необходимости ожидаются busy/in-flight, payload освобождается. Host pool GPU tier также может уменьшить RAM cache через callback ram_given. Здесь управление — связь реальных подсистем, а не только функция score. [C07, C10]

5. OLMoE CUDA: другой маршрут, полная residency экспертов

occ_start() проверяет объём всех экспертов, scratch и KV mirror с запасом 768 MiB. Он читает экспертов при setup независимо от demand CPU cache и размещает их в общем device buffer. Это не ограниченный CUDA кэш с двумя retained experts. При KV_SLOTS>1 этот chain отклоняется. Vulkan, если выбран, имеет приоритет перед этим CUDA chain. [C11]

cc_submit(1) синхронизирует recorded CUDA event. В backend также есть отдельные stream/event механизмы async fetch, но их наличие не означает, что OLMoE occ_forward использует их как наш GPU Ring. При fallback необходимо восстановить state, а не просто выбрать CPU для следующей матрицы: device может владеть более свежими KV rows. [C11, C12]

6. Vulkan expert tier и CUDA-порт общего tier

OLMoE Vulkan может использовать common vk_tier, CPU/GPU split работы экспертов и dense chain. Отдельный cu_tier.c компилирует ту же логику tier поверх CUDA operations table для движков, которые её подключили. Наличие cu_tier не превращает OLMoE occ_start в этот путь. [C10–C13]

Общий tier имеет таблицу (layer,eid), ограничение bytes/slots, форматы, очередь uploader, staging ownership, deferred evictions и inflight/join boundaries. vkt_note() копирует source bytes в собственный staging buffer до возврата; поэтому uploader не обязан удерживать caller's RAM-slot навсегда. quiesce() не освобождает занятые device allocations. Upload completion и публикация новой residency — разные события. [C10]

vkt_shutdown() останавливает и join-ит uploader, ожидает in-flight device batches, освобождает очереди и resident expert resources. Это иной lifecycle, чем detached OLMoE PILOT worker. Их нельзя объединять на схеме одним безымянным «prefetch thread». [C10]

В заголовке cu_tier.h данной версии прямо перечислены ограничения CUDA-порта: нет всех возможностей Vulkan (в частности streaming / второго device / некоторых low-bit formats и dense-chain expert table этого интерфейса). Поддержку нужно подтверждать для конкретного backend + family + format, а не по существованию одноимённой функции-заглушки. [C13]

8. Qwen: Dense/MoE и state, которые не укладываются в одну KV-картинку

qwen36 выбирает внутри слоя attention либо DeltaNet, а для отдельных семейств shortconv; после residual идёт Dense/MoE ветка moe(). Prefill/decode повторяют этот model-specific graph. Vulkan/CUDA chains и CPU remainder имеют отдельные dispatch/recovery paths. [C14]

MTP — optional отдельная ветка draft/verification/state rollback; qwen36.c подключает qwen36_mtp.h и qwen36_mtp_cuda.h и подаёт hidden rows в MTP state. Наличие этих файлов не означает, что MTP активен по умолчанию или уже подключён в AirColibri. В эту карту включена его граница; математический draft/acceptance path требует отдельного model-specific аудита.

CACHE_ROUTE тоже отдельный рычаг: в поддержанных engines может изменить набор выбранных экспертов ради residency; по документации оригинала выключен по умолчанию. PILOT прогнозирует загрузку, не подменяя реальные route ids. Для parity-ориентированного объединения эти механизмы нужно оценивать раздельно. [C16]

Другие аппаратные и распределённые ветки

Metal / unified memory: это ещё один optional backend, а не CUDA с другим названием. Документация оригинала описывает batched expert math из RAM slabs без отдельного PCIe-copy, command-buffer grouping, отдельные attention/GEMM paths и CPU fallback; исходный qwen36 также подключает Metal affine expert-store dispatch. Точность и набор операций зависят от ветки; upstream performance numbers здесь не переносились на наш компьютер. [C18]

Cluster: в documented expert-worker topology token generation, router и KV остаются у coordinator, а выбранные FFN batches отправляются workers, у которых свои disk/cache/compute. Ответы собираются перед продолжением слоя. Это другой ownership domain: локальный GPU ACK не заменяет network request lifetime/timeout. Segment/edge APIs — дополнительные границы исполнения; их нельзя считать тождественными expert-worker mode. [C19]

Metal и cluster включены как самостоятельные ветки карты. Это обзор их исходных интерфейсов и документации; все kernels/transport recovery paths в этом проходе не проверялись.

9. Serving, повторные запросы, остановка и ошибки

В OLMoE prefix ledger записывает IDs, соответствующие реальному KV. Следующий prompt может переиспользовать совпавший prefix и досчитать suffix. При нескольких KV slots модельные веса общие, состояния диалогов раздельны; decode rows могут группироваться. Prompt cancellation на CPU проверяется между слоями, оставляя прежнюю committed KV length; stale tail перезапишется. Это сложнее, чем очистка всех весов и новый cold start после каждого ответа. [C09, C17]

При аварии engine gateway может продолжить жить и перезапустить subprocess (keep_engine). Это не доказательство автоматического сохранения всех in-memory состояний сессии. Normal close сначала завершает pending requests, закрывает stdin и ждёт; затем при необходимости завершает процесс. В Windows есть job ownership для дочернего engine. [C05]

Конец CLI-run и конец embedded/segment session различаются. У OLMoE CLI часть памяти живёт до process exit; отдельные segment/edge APIs содержат собственные destroy/free functions. CUDA chain регистрирует shutdown через atexit; общий tier имеет явный shutdown. Нельзя изображать один универсальный model_free() на всех выходах. [C09, C11, C17]

Главное пересечение — цикл «получить необходимые веса → обеспечить готовность → вычислить с ними → безопасно закончить использование». AirLLM привязывает этот цикл к HF-модулям; Colibrì — к своим native слоям, expert caches и device tiers. Единая функция здесь возможна на уровне контракта данных и lifetime, но не означает одинаковую реализацию.

Второе пересечение — подготовка следующей работы заранее. Третье — продолжение генерации с накопленным state. В обоих случаях конкретные предсказатели, владельцы и способы синхронизации различаются. Именно эти различия определяют, как механизмы могут дополнять друг друга.

1. Наложение по функциям

Пунктир означает сопоставление ролей, а не реальный вызов между программами. Центральные блоки — общий смысл функции. Это аналитическое наложение, не уже реализованный общий executor.

2. Где они делают одно и то же — и насколько буквально

«Общая функция» ниже означает одинаковую обязанность в процессе. «Частично» — совпадает цель, но различаются единица работы, момент применения или контракт. Это не доказательство численной эквивалентности и не автоматическое разрешение заменить один вызов другим.

3. Точные места встречи в одной логике

До вычисления: запрос весов

HF module pre-hook и native expert_get() возникают из одного факта: следующей операции нужен конкретный объект весов. Это точка общего acquire(object, representation, consumer). На hit он возвращает lease существующего payload; на miss организует чтение и готовность. Router/математика при этом не должны зависеть от того, был ли объект в кэше.

Следовательно, можно совместить AirLLM addressable reader и Colibrì retention policy через один manager. Запуск обоих целых loaders на каждый miss не нужен. Reader выбирается по представлению данных, а не по принципу «использовать сразу обе программы».

После отправки compute: конец владения

HF post-hook и native expert_put() обозначают завершение области использования на своём уровне. Для CPU это часто конец синхронной функции. Для CUDA нужен ещё факт завершения последнего consumer. Общая точка — release intent + completion dependency, после которой manager вправе удержать объект resident, переместить его или эвиктить.

Именно здесь retention дополняет streaming: streamed forward не обязан решать судьбу веса после себя; он обязан честно вернуть владение. Наш ACK уже реализует часть этой границы, но полный общий scheduler от этого автоматически не появляется.

До следующего слоя: будущие потребности

AirLLM знает следующий модуль. Colibrì PILOT оценивает будущих экспертов по hidden state. Это разные производители заявок на будущие объекты. Их можно подключить к общей очереди, оставив demand выше speculative work, ограничив pending bytes и убирая stale requests по epoch. Предсказатели не должны сами безусловно перезаписывать буферы.

На границе прохода: состояние и корректировка размещения

У обеих программ есть проход, после которого получены logits и обновлён state. Это удобная граница для commit новых placement decisions, пересчёта state budget и осторожной смены executor. Но «граница forward» сама по себе не гарантирует, что все async consumers завершены: нужен fence именно затрагиваемых объектов.

5. Что не совпадает напрямую

  • HF/PyTorch, native C и MLX — альтернативные исполнители со своими state/layout/numerics. Их логическое место — backend selection и проверяемые границы миграции, не одновременное выполнение одного принятого token-step тремя владельцами.
  • OLMoE full-resident CUDA chain — режим для достаточной VRAM. Он дополняет малопамятный путь как другой профиль запуска, но не становится streaming chain только от добавления policy.
  • MTP — отдельная стадия draft → verify → commit/rollback. Она требует speculative state; её нельзя подмешать в обычный KV как «ещё одну предзагрузку».
  • CACHE_ROUTE — режим изменения модели исполнения ради residency. Включать только в отдельном quality track; при строгой route parity ему места в основном пути нет.
  • Metal, Vulkan, CUDA — аппаратные варианты. Их нельзя произвольно расположить во времени одного Windows/CUDA запуска, если устройство/backend не поддержаны.
  • LoRA training — отдельный жизненный цикл с backward/recompute и optimizer state; training и inference можно разделять по сеансам/версиям весов, не смешивать mutable и frozen payload.
  • Image/decision/cluster — расширения внешнего executor/service contract. Они не нужны для первого общего Dense/MoE weight lifecycle и не должны усложнять его основной путь.

Полные исходные AST-графы построены отдельно: AirLLM 715 узлов / 1 467 связей, Colibrì 24 210 / 69 599. Например, Graphify нашёл путь _pre_hook → _load_streamed_layer → load_layer_subset; исходник уточняет условие последнего перехода — expert-specialized layer path, а не каждый слой любой модели.

Найдена и конкретная ложная связь: olmoe.c::expert_get → tests/...::sleep_ms. В реальном olmoe.c это platform macro Sleep/usleep, а не вызов теста. Кроме того, vkt_note/vkt_join nodes указывают на declarations в header, тогда как поведение определено в .c. Эти места исправлены в интерпретации карты; raw Graphify output сохранён без маскировки дефектов. Поэтому функциональное наложение опирается на source anchors, а не на любую автоматически нарисованную стрелку.

3. Порядок приоритетов общей очереди

  1. Обязательный state/scratch room и текущий demand. Без них следующий корректный шаг невозможен.
  2. Уже известный ближайший объект. Например, следующий Dense layer.
  3. Предсказанные ближайшие эксперты. Допускаются, если deadline достижим и есть pending-byte quota.
  4. Долгосрочная retention/migration. Только если не отнимает ресурсы у более срочной работы.

Это исходная проверяемая policy, не утверждение её оптимальности. Стоимость read/DMA/compute, точность prediction, I/O contention и phase-specific reuse измеряются; queue priorities можно сравнивать на одном trace. Если speculative prefetch ухудшает TTFT или throughput, он должен уметь отступить без изменения вычислительного результата.

Событие «enqueue/record» и событие «completed» хранятся раздельно. Отказ speculation не должен отменять demand: необходимый объект всё равно исполняется через transient path, если он помещается в установленный budget.

6. Матрица испытаний перед включением по умолчанию

  • Числа: одинаковые inputs/weights/representation; routes, logits, KV/recurrent state. При неизменной math — bytewise oracle. При смене native math — отдельно зафиксированные численные допуски и quality protocol; не скрывать различия округления/quantization.
  • Lifetimes: delayed reader, delayed DMA, delayed consumer, occupied victim, out-of-order result, stale epoch, cancellation, failure и повторное открытие. Проверять невозможность преждевременной записи.
  • Память: globals/weights/cache/pinned/temporary/native/state/scratch, reserved и used отдельно; state growth, один объект больше slot, insufficient-room outcome. Startup gate 2.8 GiB сохраняется.
  • Полезность: cold/warm, prefill/decode отдельно; TTFT включает initialization; request latency, throughput, physical I/O и transfers; одинаковый trace для off/shadow/apply и повторные paired runs.
  • Сравнение оригиналов: standalone source paths запускаются с явно указанными representation и executor. Совпадение topology role не подменяет численную и performance проверку.

Для первого live объединения E1–E5 выбрать текущий BF16 OLMoE/HF путь, сохранив working reference, union rollback option и cache-off baseline. Qwen hybrid state проверять отдельным профилем. Native/full-chain migration подключать после соответствующих gates, а не параллельно со сменой reader, формата и scheduling policy в одном недиагностируемом эксперименте.

7. Что означает «готово»

Точки пересечения объединены, когда один trace показывает: один объект → один владелец miss и reservation → готовность → корректный consumer → подтверждённое завершение → допустимый reuse, а разные policies/backends меняют стоимость работы, сохраняя заявленный математический контракт. Режим, который корректен, но не даёт пользы на тестируемой нагрузке, остаётся optional.

Experimental; GPU expert retention remains off by default. This experiment changes physical slot layout in the existing shared pinned pool and GPU Ring. It does not introduce a weight reader, replace HF math, or connect the full native Colibrì model executor.

The previous GPU-cache report used a union template: every slot reserved space for both Dense and expert tensors. The new compact layout reserves slot 0 for the Dense trunk and the remaining slots for experts. union remains available for comparison/rollback. Both arenas still use one allocation each, with validated, disjoint byte offsets.

Physical reservations

For the tested OLMoE-1B-7B BF16 checkpoint:

Configuration Historical union Compact Reduction in each arena
No retained GPU experts: Dense + scratch expert 92 MiB 46 MiB 46 MiB
Two retained GPU experts: four slots total 184 MiB 70 MiB 114 MiB

Compact geometry is 34 MiB Dense + 12 MiB per expert slot. The four-slot layout is 34 + 12 + 12 + 12 MiB; optional retention adds 24 MiB GPU and 24 MiB pinned RAM. These are weight-arena reservations, not total process memory. Globals, activations, KV, allocator reservations and native/runtime allocations remain additional memory.

The shared MoE CLI defaults to --moe-slot-layout compact; --gpu-expert-slots still defaults to zero. plan and runtime use the same geometry builder. Wrong-role, missing or mismatched payloads are checked against the actual destination slot before any write/DMA.
